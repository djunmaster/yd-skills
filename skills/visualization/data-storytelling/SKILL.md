# Data Storytelling

## 目标

把复杂材料重构为**有完整逻辑主线、有真实视觉画面、可核查、可复用**的叙事单元。让读者不只读文字大纲，而是通过**可视化 SVG 界面/图画**一眼看懂画面里的机制、空间、状态与对比，再顺着清晰的 **`1、2、3、4、5、6` 分点逻辑说明**层层理解“为什么、怎么发生、边界在哪、下一步做什么”。

优先生成适合当前宿主的图形表达。普通对话中，对复杂趋势、机制、比较或场景使用 `$visualize`；如果环境只能输出代码，再使用 Mermaid。对 HTML、网页或视觉报告，默认使用本 skill 的 **SVG 视觉画面优先 + 编号逻辑叙事**深色技术讲解版——把抽象逻辑画成具象界面、物件场景、物理机关、前后分屏或仪表视窗，绝不退化成“一堆圆角方框+箭头的框线图”或“一张总图 + 零散文字堆叠”。

## 默认触发与自适应输出

当用户只说“帮我整理这段内容”“总结一下”“梳理这份材料”或意思相近的话，并附带一段有实质信息的文本、链接、文件或会议记录时，自动采用本 skill 的结构，不要求用户点名 `data-storytelling`，也不要求用户预先指定图形类型。

先理清全文的因果递进主线，再选择最合适的表达组合：

- **有完整因果、阶段或方法演进时**：开篇给出整页逻辑总纲（`1 → 2 → 3 → 4 → 5 → 6`），章节间用承上启下句衔接。
- **有核心机制、交互界面、空间场景或状态对比时**：画宽幅可视化 SVG 画面（带 `1–6` 编号锚点），并在图下用 `1、2、3、4、5、6` 分点讲透逻辑。
- **某一个分点需要放大反例或微观结构时**：把局部特写 SVG 直接嵌入该分点内，不脱离正文散落成孤立卡片墙。
- **内容包含明确判断条件或落地动作时**：按 `1、2、3、4、5、6` 逐点配具象视觉对比或操作产物，并补边界与执行清单。
- **没有足够信息支持图形时**：使用编号结构化文字、对照表或 Mermaid；绝不为了“有图”而虚构数据或结构。

默认按“**一句话主结论 → 整页逻辑总纲（1→N）→ 分章（承上引子 + 可视化 SVG 主画面 + 1、2、3、4、5、6 分点逻辑说明 + 局部特写/边界 + 启下过渡）→ 执行清单 → 已验证事实/推断/待验证问题**”输出。内容简单时压缩章数；内容复杂时按逻辑递进展开章节，而不是机械堆砌几十张碎框图。

## 可视化 SVG 图画原则（反框线图硬约束）

本 skill 生成的 SVG **不是“圆角矩形里写字 + 箭头连线”的逻辑流程框图**，而是**用图画和可视化界面去讲述内容**。画任何图前必读 `references/visual-svg-cookbook.md`。

1. **强制通过“去字可辨检验（Text-Removal Test）”**：
   - 假设把 SVG 中的全部中文文字抹掉，读者依然能看出这张图画的是什么界面、物体、机关或状态对比（例如：带气泡的聊天窗口与抽离卡片、带红绿 diff 的代码编辑器、被斜纹隔断墙分开的双盲工位、盖着斜纹遮蔽条的脱敏文档、带挂锁与隔离墙的考卷库、带放大镜的设备局部）。
   - 如果抹掉文字后只剩几个均匀的圆角矩形和直角箭头，说明退化成了框线图，**必须推倒重画**。
2. **禁止把“方框 + 箭头”当默认答案**：
   - 只有在“拓扑顺序本身就是唯一重点”时，才允许使用 `data-visual-mode="diagram"`。
   - 其余所有软件/AI/业务/规则/数据/物理场景，优先选用七类可视化原型之一并声明 `data-visual-mode`：`interface`（可视化界面/工作台）、`scene`（现实/空间场景）、`metaphor`（视觉隐喻）、`mechanism`（可视化机关）、`before-after`（前后视觉分屏）、`cutaway`（立体分层/剖面）、`chart`（仪表/曲线观测视窗）。
3. **图文面积预算与宽画布舞台**：
   - **60%–75% 给视觉画面本身**（窗口框架、控件、物体轮廓、斜纹纹理、隔断墙、空槽、放大镜、状态指示器），**25%–40% 给短标签与编号锚点**。
   - **章节主视觉画面推荐 `viewBox="0 0 920 420"` ～ `960×460`**（全宽展示），给具象画面和 14px+ 标签留足呼吸感；局部特写图用 `560×300` ～ `680×340`。禁止再用拥挤的 `480×300` 强塞多块文字方框。
4. **四层视觉质感（锁定深色色板，克制且有层次）**：
   - Layer 0 舞台底（`data-backdrop="true"` + `.s-stage` + `<pattern>` 点阵/微网格）；
   - Layer 1 主视觉界面/物体表面（窗口顶栏三点、折角文档、骨架横线、物体轮廓、微渐变表面）；
   - Layer 2 语义信号层（橙色/红色斜纹 `<pattern>` 表示遮蔽/合成/隔断/禁区，虚线空槽 `.s-socket` 表示缺口，挂锁/印章/放大镜 `.s-loupe` 传递关键状态）；
   - Layer 3 编号锚点层（`data-callout-badge="1"`…`"6"` + `data-badge-shape="true"` + 精准引线 `data-callout-leader` 与目标小圆点），与图外 `1、2、3、4、5、6` 分点说明精准同步。
5. **抽象逻辑也要画成“可看见的画面”，但不伪造数据**：
   - 对话/文档/知识检索 → 聊天窗口消息流 + 高亮选区括号 + 抽出的带 `[引用ID]` 知识卡；
   - 代码/字段变化 → 分屏代码 diff 视窗或结构化表单对比（原句高亮 → 对应字段）；
   - 隐私脱敏/权限边界 → 文档原件穿过光学滤镜变成带斜纹遮蔽条的脱敏卡 + 挂锁授权包；
   - 质检/拦截 → 带 4 个字段小格的卡片经过扫描分拣闸，带虚线空槽的卡片分流进退回滑道；
   - 双盲复核/分歧仲裁 → 中间立斜纹隔断墙的双工位 + 不同色判定印章 + 冲突灯导向仲裁规范书；
   - 长尾缺口/合成补位 → 实心样本阵列 + 发光虚线空槽 + 斜纹合成补片；无真实数值时标明“示意，非实测”；
   - 阈值/曲线 → 示波监测视窗 + 关注区带 + 交点圆点；原文未给阈值时拆开观察事实、待补专家规则和可能等级，绝不自造阈值或三色波形；
   - 现实空间 → 完整或局部物体轮廓 + `data-target-for` 目标框 + 放大镜特写，明确区分图像定位候选、原文业务简化规则和已证实物理事实。
6. **严守布局契约与几何验收**：
   - 新生成的复杂 SVG 必须声明 `data-layout-contract="v1"` 与 `data-visual-mode="..."`。
   - 锁定 viewBox、24px 安全边距、16px 节点间距、8px 文字内边距、6px 连线净距；核心标签实际渲染字号 `>= 14px`，次要说明 `>= 12px`；编号锚点圆半径 `r >= 14`，引线严禁压字。完整规范见 `references/svg-layout-protocol.md`。

## HTML 页面整体逻辑与 1、2、3、4、5、6 分点叙事架构（硬约束）

生成完整 HTML 讲解页时，**逻辑连贯性优先于机械切图**。严禁“给每个孤立关系随便画一张小框图，再在下面堆几句零散文字、`.kv-grid` 和 `.takeaway` 凑页面”。必须构建三层逻辑架构：

1. **第一层：整页因果主线（Hero + `.story-roadmap`）**
   - Hero 用 `.deck` 一句话点出核心总判断，随后用 `.story-roadmap` 列出整页 **`1 → 2 → 3 → 4 → 5 → 6`**（按实际章数，通常 4–6 章）可点击逻辑路标。
   - 每个路标说清**推进逻辑**（如 `1. 痛点根源 → 2. 数据切分机制 → 3. 双盲质控防线 → 4. 隐私与考卷隔离 → 5. 方法选型判断 → 6. 落地执行清单`），而不是堆砌互不相连的词条标签。
2. **第二层：章与章之间“承上启下”（`.section-bridge` + `.next-bridge`）**
   - 除首章外，每章顶部用 `.section-bridge` 明确承接上一章（“上一章解决了 X，但带来了新问题 Y，因此这一章聚焦……”）。
   - 每章结尾用 `.takeaway` 收束核心结论，有风险或前提时紧跟 `.caution`，并用 `.next-bridge` 自然引向下一章。
3. **第三层：章内「可视化 SVG 主图 + 1、2、3、4、5、6 分点联动说明」（`.logic-points`）**
   - 每章先用 **1 张宽幅可视化 SVG 画面（`920×420` 级别）**把本章的完整界面、场景或机制直观画出来，在画面关键节点按自然阅读顺序标上 **`1`、`2`、`3`、`4`、`5`、`6`** 圆形锚点（`data-callout-badge="1"`…`"6"`）。
   - 图下紧接 `<ol class="logic-points" data-for-visual="<visual-id>">`，按 **`1、2、3、4、5、6`** 逐点展开：
     - 每条 `<li class="logic-point" data-point="1">` 包含：同色系编号圆章 `.point-num`（`1`～`6`）、加粗主判断标题、语义角色胶囊 `.point-role`（如 `现状痛点` / `核心机制` / `关键动作` / `判断门槛` / `易错边界` / `最终产物`）、以及 1–3 句讲透“看到什么 → 为什么会这样 → 如何推向下一步”的逻辑说明。
     - 避免把所有文字塞进 SVG，也避免把无编号的零散段落堆叠在图下。
   - **局部特写按需内嵌（`.point-visual`）**：当某一个分点（例如第 4 点或某个反例/案例对比）需要独立的可视化画面展开时，把特写 `figure.viz` 嵌在对应 `.logic-point` 的 `.point-visual` 里，让图示始终服务于当前逻辑点，而不是脱离逻辑漂浮在 2 列卡片墙里。
4. **按视觉理解需求决定图数，兼顾完整覆盖与叙事紧凑**：
   - 一个完整的 4–6 步逻辑机制，优先由 **1 张带 `1–6` 编号锚点的富视觉 SVG 主画面 + 同步的 `1、2、3、4、5、6` 分点逻辑说明**讲清；不要把连续逻辑硬拆成 6 张孤立的 480px 文字方框。
   - 对于多案例、多判断项或多执行步骤的内容：若各项共用同一机制视角，用带 `1–6` 锚点的全景可视化工作台 + `1–6` 分点拆解；若每项有截然不同的可视化界面、空间结构或前后对比，则在对应编号分点（`1、2、3、4、5、6`）下逐项配独立可视化 SVG 画面，并在分组容器上用 `data-required-visuals` 登记覆盖。
   - 贯穿教学案例先冻结原文、记录 ID、字段、标签和复核状态，标明“教学示意 / 非实测”，后续各点不得擅自添造时间、结论或指标。

## 可读性与语义自检（硬约束）

1. **清晰度高于塞满**：每张 SVG 只聚焦一个核心画面或机制主题，视觉焦点只能有一个；背景说明、边界条件、多步推理放进图外 `1、2、3、4、5、6` 分点说明、`.caution` 或 `.evidence`。
2. **字号与间距底线**：核心标签实际渲染字号不得低于 `14px`，次要说明不得低于 `12px`。禁止用 9–11px 或缩小 SVG 显示宽度硬塞内容。
3. **窄屏横向滚动不缩图**：整图缩放会让字号和线宽同比缩水，审计按 `FIGURE_SHRUNK` 报错。构建脚本会自动按 viewBox 宽度写入 `--viz-min-w`；手写页面须补同名声明。出现横向滚动时必须有可见滑动提示（防 `SWIPE_HINT_MISSING`）。
4. **视觉权重层级**：主对象/关键界面框线 `2.2–3px`，次级容器 `1.8–2px`，辅助线与引线 `1.5–2px`，虚线只表候选/边界/空槽/回流。关键标题与结论加粗（`700–800`），解释句保持常规字重。颜色只做辅助，形状、斜纹、图标与标签同时传递含义。
5. **真实对象与空间边界**：目标框 `data-target-for` 必须对应原文定义的对象；框相交只表图像定位候选，可见接触不等于电气接通或合规接地；现实物体朝向、铰链与连接点须有参考或标明“结构示意，细节待核实”。
6. **证据诚实与逐图复核**：交付前对照原文检查每张图的可见事实、适用规则、待补缺口与编号同步（`LOGIC SYNC`），几何 `PASS` 不能代替视觉质量、逻辑连贯性或语义正确性。具体门槛与课程原文示例见 [语义与证据门槛](references/svg-layout-protocol.md#语义与证据门槛)。

## 并行子 Agent 生产协议

当任务包含 3 张以上复杂可视化 SVG 或完整长 HTML 页面时，默认使用并行生产。详细模板见 `references/subagent-orchestration.md`。

1. Lead Agent 先完成**整页逻辑主线（1→N 章节与承上启下）+ 章内 `1、2、3、4、5、6` 分点大纲 + 每张图的视觉画面方案（`visualMode`、`visualScene`、`callouts`）+ 固定契约**，并传递相关原文片段、规则来源与未知点；契约冻结前不启动绘图 Agent。
2. 每个 Figure Worker 只画一张可视化 SVG（必读 `references/visual-svg-cookbook.md`），先产出 `spec.json` 再写 `figures/<visual-id>/figure.html`；不得修改全局 CSS、页面骨架或其他图。
3. Auditor 分别报告**几何（`audit_svg_layout.py --strict`）、去框线图视觉质量（去字可辨）、逻辑与 `1–6` 编号同步、语义证据、可读性**五项审核结果；失败项交回原 Worker 修复。
4. Lead 合并全部通过的片段，再运行整页桌面端与移动端严格审计，并人工查看渲染截图确认画面质感与逻辑顺畅度。
5. 连续两轮仍无法解决拥挤或碰撞的图，应精简图内文字（把解释移到图外 `1–6` 分点）或拆出局部特写，不要继续硬挪坐标。

## 处理流程

1. **读材料建事实表**：提炼主题、核心矛盾、对象、机制、条件、指标、证据来源与未知点；分清原文陈述、业务简化规则、独立验证事实、合理归纳和待补项。
2. **先立逻辑骨架，再做视觉设计**：
   - 先写出整页 `1 → 2 → 3 → 4 → 5 → 6`（按实际章数）因果递进主线，确定每章的承上启下问题；
   - 为每章写出 **`1、2、3、4、5、6` 编号逻辑分点**，确认点与点之间有清晰的因果、递进或条件推进，而不是无序罗列。
3. **为每章构思具象的 SVG 视觉画面**：
   - 对照 `references/visual-svg-cookbook.md`，决定用哪种视觉界面、物理场景、视觉隐喻或前后分屏来呈现本章逻辑；
   - 列出画面必须包含的非方框视觉元素（`visualProps`）和 `1`～`6` 编号锚点落位，并做“去字可辨检验”；
   - 若某个编号分点需要独立放大细节或反例，为其规划嵌入式局部特写图（`.point-visual`）。
4. **编写图文联动页面**：
   - 画面承载“一眼看懂的结构、界面、状态与对比”，图外 `1、2、3、4、5、6` 分点说明承载“为什么、怎么推进、边界和动作”；
   - 文字不要机械重复读图，要讲清因果关联与下一步判断；
   - 保留证据边界（`.evidence`）与风险提示（`.caution`）。
5. **自动审计 + 截图目检**：
   - 运行桌面端与移动端 `audit_svg_layout.py --strict`，检查几何、视觉原语（无 `VISUAL_TOO_SCHEMATIC`）、编号同步（`LOGIC SYNC PASS`）与覆盖声明；
   - 打开渲染截图逐图核对视觉质感、去字可辨度、文字清晰度和整页逻辑阅读体验。

## 图形选择规则

- **软件交互、对话切分、代码修改、文档检索、表单/字段处理**：可视化界面工作台（`interface-scene`，带窗口栏、气泡/代码 diff/高亮选区/引用卡片）。
- **现实设备、车辆、现场作业、空间包含与接触**：现实场景图 + 局部放大镜（`physical-scene`，一致朝向、目标框 `data-target-for`、放大镜特写）。
- **双盲复核、质检拦截、权限隔离、版本切换、长尾补位、防泄漏评估**：视觉机制与隐喻图画（`metaphor-mechanism`，斜纹隔断墙、扫描分拣闸、挂锁与防火墙、活页版本架、空槽补片）。
- **治理前后、脱敏前后、重构前后、错误 vs 正解**：前后视觉分屏（`before-after-stage`，左异常/原始 → 中滤镜/转换器 → 右洁净/遮蔽/校验通过）。
- **系统架构、数据底座、权限层次**：立体分层面板/剖面（`cutaway`，错位层板 + 垂直通道 + 层内微型物件）。
- **曲线、阈值与等级判读**：仪器监测视窗（`instrument-chart`，微网格底 + 关注区间带 + 交点圆点；原文缺判据时拆开观察事实与待补专家规则，不自造阈值或三色波形）。
- **长尾与分布**：密度/样本阵列或相对柱图；无真实数据时明示“示意，非实测”。
- **整页总览与多阶段演进**：带 `1–6` 路标锚点的视觉全景地图（`story-map`）+ `.story-roadmap`。
- **纯流程拓扑**：仅在步骤连接拓扑本身就是重点时用 `diagram`，并附具象产物形态与 `.logic-points` 编号说明。

## 长文本总结模式

对于会议录音、访谈、研究报告或多篇材料：

- **先提炼一条有因果推进的逻辑总主线（1→N 章）**，不要按发言碎片流水账直接切碎成几十张卡片。
- 每章用**可视化 SVG 主画面 + `1、2、3、4、5、6` 编号分点**串联：案例按“1.现场痛点 → 2.原始形态 → 3.核心改造 → 4.质控/规则 → 5.验证结果 → 6.边界与复用”递进；方法论按“1.输入 → 2.处理机制 → 3.关键判断 → 4.输出产物 → 5.反馈迭代 → 6.避坑边界”展开。
- 对含有口语、转写错误或观点冲突的材料，保留原意但不把不确定说法改写成事实。
- 对缺少数值的比例关系，使用“相对示意”画面并明确标注；对课程、访谈或口述案例，保留“课程口径 / 未独立核验”等证据边界。

## 大模型微调与数据建设的默认方法论

将微调视为“任务定义、数据、评估、迭代”的工程闭环，而不是一次训练动作：

1. 先定义真实场景和可测输出，再决定是否需要微调。先用提示词、检索或工具调用建立基线；只有当问题具有稳定任务边界、可积累示例、且基线不足时才进入微调。
2. 拆任务而不是笼统地说“训练一个智能体”。把输入类型、输出格式、错误类型、允许的人工介入和验收指标写清楚。复杂业务优先拆成多个可观测子任务。
3. 建训练集、验证集、测试集并锁定划分规则。测试集应代表真实输入，避免同源样本、增强副本、同一事件或同一用户同时进入训练和测试。
4. 训练样本遵循“输入足够多样、输出足够一致、格式贴近生产”。混合正常、边界、困难、拒答和异常样本；用少量高质量样本校正方向，持续补充模型失败样本。
5. 评估不只看平均分。按场景、类别、长尾、严重错误和成本/延迟拆分指标；对关键错误建立人工复核。模型预测与既有标注差异大、loss 高的样本可作为标注反查入口，但必须人工确认。
6. 数据治理覆盖来源权限、隐私合规、清洗、标注、标准化、元数据、质量检查和可追溯版本。至少记录来源、用途、字段定义、标签规范、数据集版本、处理脚本、评估结果和责任人。
7. 对视觉或多模态数据，先检查清晰度、曝光、分辨率、坐标、码流、时间同步和标注对齐；用 embedding 相似度识别重复或增强注水；针对长尾补采真实困难样本，合成数据只作为有约束的补充。
8. 用“首版可用→模型反查→补失败样本→再训练”的数据飞轮推进。首批数据不必追求完美，但每轮都要记录变更、评估集版本和失败类型，否则无法解释模型是否真的变好。
9. 微调方式按目标选择：监督微调适合稳定的输入到输出映射、格式和行为；偏好优化适合风格、排序、摘要取舍；检索增强适合知识经常变化且需要引用来源；视觉微调适合图像输入理解问题。不能用微调替代实时知识库、权限控制或业务规则。

## 输出约定

默认输出顺序：

1. 一句总判断 + 整页 **`1 → 2 → 3 → 4 → 5 → 6`** 逻辑主线（`.story-roadmap`）。
2. 按逻辑递进展开各章：每章包含**承上引子（`.section-bridge`）→ 宽幅可视化 SVG 主画面（带 `1–6` 编号锚点）→ 同步的 `1、2、3、4、5、6` 分点逻辑说明（`.logic-points`，需特写时在对应分点内嵌 `.point-visual`）→ 收束判断/风险边界与启下过渡（`.next-bridge`）**。
3. 可复用的判断框架或执行清单（同样采用清晰编号与具象视觉）。
4. 已验证事实、基于证据的归纳、待验证问题（`.evidence`）。

如果用户明确只要文字，保持同样的“主线 + 1、2、3、4、5、6 递进逻辑”结构，但不生成可视化。若用户要求图片、网页或演示文件，先确认目标格式与尺寸，再调用相应工具或技能；不要把内联可视化误当成已交付的独立文件。

## 几何与图文同步验收（硬门槛）

深色技术讲解页、独立 SVG 图解和任何使用 `data-layout-contract="v1"` 的页面，交付前运行：

```powershell
python scripts/audit_svg_layout.py output.html --channel msedge --strict `
  --json layout-report.json --screenshot layout-check.png

python scripts/audit_svg_layout.py output.html --channel msedge --strict `
  --viewport 390x844 --json mobile-layout-report.json --screenshot mobile-layout-check.png
```

必须满足：

- 每个契约图返回 `PASS`（无 `error` 与 `warning`）；旧图必须返回基础扫描 `PASS`，不能只返回 `SKIP`。
- 无节点重叠、文字溢出、文字重叠、连线穿框、连线穿字、连线交叉、标签压线、锚点文字溢出（`BADGE_TEXT_OVERFLOW`）、锚点重叠（`CALLOUT_BADGE_OVERLAP`）和 viewBox 越界。
- 声明为可视化画面的图（`interface` / `scene` / `metaphor` / `mechanism` / `before-after` / `cutaway`）不得触发 `VISUAL_TOO_SCHEMATIC`。
- 绑定 `data-for-visual` 的 `.logic-points` 与对应 SVG 的 `data-callout-badge` 必须返回 `LOGIC SYNC PASS`（无 `CALLOUT_POINT_MISMATCH`）。
- 声明 `data-required-visuals` 的分组内，每个应有条目都能找到唯一的 `figure.viz` 和实际 SVG。
- 浏览器控制台和页面脚本无错误，桌面与移动端均无横向溢出、无整图缩放（`FIGURE_SHRUNK`）、无缺滑动提示（`SWIPE_HINT_MISSING`）。
- **自动审计通过后必须查看渲染截图**，结合原文确认：是否真正通过“去字可辨检验”、画面主次是否鲜明、逻辑与 `1–6` 分点是否顺畅、语义和证据边界是否诚实。

若自动审计与截图结论冲突，先修图；不能以“看起来还行”覆盖机器报告。

## HTML 页面交付（两种锁定风格）

当用户要求生成网页、HTML 页面，或要求“图表 + 文字”的完整展示时，必须使用本 skill 的现成视觉系统，不要临时自创配色、字体、渐变或组件风格。

### 风格选择

- **深色技术讲解版（默认）**：深色卡片、蓝紫/绿/橙语义视觉画面 SVG、可视化界面工作台、现实场景标注、视觉隐喻图与 `1、2、3、4、5、6` 编号逻辑叙事。适合技术培训、方法论复盘、产品逻辑拆解、案例讲解、数据和 AI 主题。
- **QQ 浅色分享页版**：仅在用户明确要求复刻最初的 `r.qq.com` 分享页、要求浅色底，或明确说保留上一版风格时使用。

### 深色技术讲解版（默认）

- **首选结构参考**：`assets/visual-story-demo-body.html`（新版“可视化 SVG 画面 + 整页主线 + 1、2、3、4、5、6 分点联动”完整示范）。`assets/dark-story-body.html` 保留为历史多案例兼容样本；整理新材料时一律以新版结构为准，并按新内容重建逻辑线、视觉画面与覆盖声明，不把旧案例或示例 ID 带入新材料。
