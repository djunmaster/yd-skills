# Data Storytelling

## 目标

把材料变成可读、可核查、可复用的叙事单元。每个单元都回答一个明确问题：有哪些对象、它们如何连接、变化发生在哪里、读者应该得出什么判断。

优先生成适合当前宿主的图形表达。普通对话中，对复杂趋势、机制、比较或场景，宿主提供内联可视化能力时优先使用；没有该能力时，直接输出本 skill 的内联 SVG 或 HTML，只能输出纯文本时再使用 Mermaid。对 HTML、网页或视觉报告，默认使用本 skill 的 SVG-first 深色技术讲解版，把抽象判断画成可观察的对象、空间、阈值、分布或流程；不要退化成“一张总图 + 大段文字”。

## 默认触发与自适应输出

当用户只说“帮我整理这段内容”“总结一下”“梳理这份材料”或意思相近的话，并附带一段有实质信息的文本、链接、文件或会议记录时，自动采用本 skill 的结构，不要求用户点名 `data-storytelling`，也不要求用户预先指定图形类型。

先根据材料的关系选择最合适的表达组合：

- 有总的因果、阶段或流程关系时，给出总览图。
- 信息点较多且各自有独立关系时，拆成多张视觉卡片。
- 关系图不能表达证据、原因、边界或判断时，补充文字解释。
- 内容包含明确动作、落地步骤或决策项时，给出执行清单。
- 没有足够信息支持图形时，使用结构化文字、对照表或 Mermaid；不要为了“有图”而虚构数据。

默认按“主结论 → 总览图 → 视觉卡片 → 文字解释 → 执行清单 → 已验证事实/推断/待验证问题”输出。内容简单时可以压缩结构；内容复杂时应扩大卡片覆盖范围，而不是只给一张概览图。

## SVG-first 覆盖规则（硬约束）

当目标包含图形化讲解或 HTML 页面时，按以下规则执行：

1. 先建立“信息单元清单”。一个信息单元可以是一段独立判断、因果、对比、步骤、阈值、角色协作、分布、案例结论或行动建议。
2. 除过渡句和纯连接词外，**每个有独立含义的段落至少对应一张 `figure.viz`**。一张图只回答一个问题，不能把六种关系塞进一张大图。
3. 每张图必须有：短标题、关系句、图中关键标注、图注结论。复杂图再补证据、边界或行动建议。
4. 长文不要只用一张总览图收尾。总览交代主线，案例中的独立做法分别画图，判断表与执行清单也逐项配图；章节末尾放一张文字清单不能算覆盖了其中的所有动作。
5. 抽象内容也要画，但画的是关系，不是虚构数据：
   - 对象与输入输出：画带类型的对象、字段和映射箭头。
   - 阈值与判断：原文给出判别条件时才画对应区间和等级映射；条件缺失时拆开曲线事实、专家规则和可能的等级输出，并标明规则待补。
   - 空间关系：画目标框、包含、相交或可见连接，并区分图像定位候选、原文业务规则和物理事实。
   - 分布与长尾：没有真实数值时只画相对柱高，并明确“示意，非实测”。
   - 角色协作：画谁产出什么、谁复核、分歧如何仲裁。
   - 版本与迭代：画数据版本、模型版本和指标的对应关系。
6. 没有数值时可画对象关系、示例记录、前后变化或操作产物。只有编号、图标、概念方框或一段加粗文字的卡片不算解释图。信息确实不足以画出关系时，保留文字并明确缺口，不伪造数据或结构。
7. 禁止把“方框 + 箭头”当默认答案。只有流程本身是重点时才用流程图；有现实对象时优先画对象场景，有空间关系时优先画框与位置，已定义阈值时才画阈值带，有分布时优先画图。
8. 新生成的复杂 SVG 必须使用 `data-layout-contract="v1"`。节点用 `<g data-node>`，连线用 `data-link/data-from/data-to`，连线标签用 `data-link-label/data-for`。完整规范见 `references/svg-layout-protocol.md`。
9. 先画布局，再画美化。锁定 viewBox、24px 安全边距、16px 节点间距、8px 文字内边距、6px 连线净距和零交叉默认值；不要靠缩小字号或压线塞内容。
10. 一张图超过 7 个节点、8 条连线或需要三次以上拐弯时，优先拆图。不能同时说明五个判断的图，应拆成多张单一关系图。
11. 布局几何必须由浏览器验证，不能由模型目测。新图必须通过 `audit_svg_layout.py --strict` 的契约审计；未声明契约的旧图也必须通过文字/路径基础扫描，不能静默跳过。几何 `PASS` 不代表可读性或语义正确性通过。
12. 关系箭头必须指向可见且命名的具体对象，并绑定有效的 `data-from/data-to`。修改旧图中的关系箭头时，将该图升级为 `v1`；旧图基础扫描不验证箭头端点。反馈关系若需要额外解释来源、复核和去向，单独画一张小图，不用停在空白处的长回流线暗示闭环。具体端点规则见布局协议。

## 判断与行动的逐项图解

适用于完整图文讲解页，包括案例正文、选择表、执行清单和补充说明；不要只在页面前半部分放图。

- 判断项画清“看见什么缺口 → 为什么选这个方法”。例如用任务覆盖空位解释合成补位，用两个专家对同一样本的不同标签解释分歧复核。图注说明适用条件和限制。
- 行动项画清“拿到什么输入 → 具体改了什么 → 留下什么产物”。例如展示原始工单到结构化样本的字段变化、训练池与固定测试集的分离、数据/模型/评估版本的对应。不能只把“采集、清洗、标注”各装进一个方框。
- 长步骤可以拆为多张小图，同一张图保持一个关系。按内容数量决定图数，不用固定的 8–15 张上限反过来删减内容。
- 优先串联一个具体教学案例，帮助读者看懂各步骤之间的衔接。示例记录、伪代码、示例答案和假设值都必须标明身份，不能冒充课程案例或生产数据。
- 贯穿示例先冻结原文、记录 ID、字段、标签和复核状态。后续图不能自行增加时间、设备号、处置证据或最终结论；补充信息须说明来源。独立示例换 ID，字段节选注明节选，完整输出遵守同一任务约定。
- 用图外加粗句说明关键变化，再说明本步可交付的文件、字段、规则或检查结果。没有原文支持的标准、阈值和审批结论保留待确认。
- 在页面分组容器上用 `data-required-visuals="visual-id-1 visual-id-2"` 登记应有图解。审计器检查每个条目是否在本组中存在且含 SVG；该检查只证明结构覆盖，Lead 仍须逐项确认图是否解释了内容。

## 小图优先与语义自检（硬约束）

图表不是为了把整页填满，而是为了让读者逐个看清关系。默认先判断能否用小图、卡片或矩阵表达；只有总主线必须同时出现时，才使用整页宽图。

1. 一张图只回答一个问题。出现多个独立判断或多套判别规则时，先拆成多张单关系小图；同一关系所需的多个对象可以保留在一起，典型尺寸为 520×280 或 560×300。
2. 小图只保留理解该关系所需的对象、框、线和结论。案例背景、指标口径和边界说明放到图注、正文卡片或执行清单，不要塞回 SVG。
3. 核心标签实际渲染字号不得低于 14px，次要说明不得低于 12px。禁止用 9px、10px、11px 或缩小 SVG 显示宽度来硬塞内容；字号和留白冲突时先拆图或删信息。
4. 图标、编号和文字必须分区。不要让图标与标签挤在同一狭小节点里；标签放在图标外侧的独立标注带，并保留可见净距。
5. 目标框和标注框必须对应原文定义及标签所指的对象。原文检测卸油车整体时保留整体目标；若标签指接地端子，就必须标出该端子，不能用车身或车轮代替。
6. 空间图按关系所需选择整体或局部。检测框只定位候选对象，框相交只表示图像中的框关系；可见接触也不能证明电气接通或合规接地。将原文中的业务简化规则与已证实物理事实分开标注。
7. 现实物体的外形、朝向、铰链和连接点应有合理结构及原文、现场图像或可靠参考支持；参考不足时标明结构示意与未知点，示意图不作现场证据。
8. 交付前逐图核对原文、图中可见事实、适用规则和结论，独立检查读者能否对应对象、曲线、区域与标签。具体门槛及虚构内容的应用示例见 [语义与证据门槛](references/svg-layout-protocol.md#语义与证据门槛)，不能用加粗或几何 `PASS` 代替。
9. 移动端保留横向滚动时，必须给出“左右滑动查看完整图示”的可见提示；不得为了适配窄屏把字号压到 12px 以下。

## 视觉权重与逻辑层级（硬约束）

参考深色技术讲解页时，清晰度来自主次分明、线框有重量、文字有层级，而不是把所有元素同时加粗。每张视觉单元必须先让读者看见主判断，再看对象和证据，最后读提示或边界。

1. 每张图先写一句唯一关系句，再拆成三层：**主判断**、对象/路径证据、限制或注意事项。主判断使用更大、更粗、更高对比度的标签；证据使用中等字号；背景说明移到图注或正文。
2. SVG 线框使用明确的重量层级：主对象框约 2–3px，关键路径约 2.5–3px，辅助线约 1.5–2px，虚线只表示边界、候选或回流。不要让所有线条都使用同一细线。
3. 关键对象的框要比普通容器更醒目，并使用标签、颜色和形状同时表达含义。颜色只做辅助，不能让读者必须依赖颜色才能理解关系。
4. 关键文字默认加粗：图标题、步骤编号、对象名称、判断结论、风险词和数字指标使用 `font-weight: 700–800`；解释句保持常规字重，避免整张图变成一块粗体。
5. 重要提醒必须有独立的强调块：结论用 `.takeaway`，风险/误区用 `.caution`，证据边界用 `.evidence`。不要把注意事项缩成 SVG 角落里的小字。
6. 有明确先后顺序时，除了图内箭头，再用独立的 `.logic-strip` 或编号卡说明 `01 → 02 → 03`；不要让顺序只依赖一条穿过多个对象的长线。
7. 一段文字同时包含场景、判断规则、执行步骤和结果时，拆成多张 SVG：场景图回答“看什么”，规则图回答“如何判断”，顺序图回答“先做什么”，结果卡回答“得到什么”。图与图之间用编号和一句过渡话连接。
8. 不要把“场景 + 多个行为 + 任务定义 + 结果 + 注意事项”塞进一张图。单张图宁可只画一个对象和一个框，也不要为了覆盖全文牺牲准确性。
9. 每张图的视觉焦点只能有一个。若读者需要在两个同等重量的框之间来回猜测主次，拆图或降低次要元素的线宽、字号和填色。

## 并行子 Agent 生产协议

当任务包含 4 张以上图或完整 HTML 页面时，默认使用并行生产，避免一个 Agent 在长页面里反复修坐标。详细模板见 `references/subagent-orchestration.md`。

1. Lead Agent 先完成语义拆解、视觉清单和固定契约，并传递相关原文片段、规则来源与未知点；契约冻结前不启动绘图 Agent。
2. 每个 Figure Worker 只画一张图，只写 `figures/<visual-id>.html`；不得修改全局 CSS、页面骨架或其他图。
3. Auditor 对每个片段分别报告几何、语义和可读性审核结果；按 `references/subagent-orchestration.md` 的提示模板核对原文与图，失败片段交回原 Worker 修复。
4. Lead 合并三项审核均通过的片段，再运行整页布局、移动端、控制台和内容覆盖检查。
5. 并行只用于彼此独立的图。同一张图内部的节点、通道和标签必须串行确定。

加速原则：规划一次、并行绘图、每图两轮几何修复、最后只做一次整页验收。连续两轮仍失败的图应拆图，而不是继续堆坐标。

## 处理流程

依赖说明：几何审计脚本 `scripts/audit_svg_layout.py` 需要 Python 与 Playwright（`pip install playwright` 后 `playwright install msedge`，或本机已有 Edge/Chrome）。运行环境缺少这些依赖时，不要声称已完成几何验证，改用逐图人工核对截图并如实标注未验证。

1. 先读材料并建立事实表：主题、对象、动作、条件、指标、时间、证据来源、未知点。把原文陈述、业务启发规则、独立验证事实、合理归纳和待定义项分开。
2. 先判断输入输出：用户要看趋势、流程、闭环、层级、对照、案例、检查、分类还是机制。不要先选图形再硬塞内容。
3. 把一个长主题拆成若干“视觉单元”。为每个单元登记 `title`、`visual_type`、`relation`、`must_show`、`labels`、`focus`、`sequence`、`callout`、`caution`、`evidence`、`boundary`；一个单元只承载一个关系或一个判断。
4. 为每张卡片写一个短标题、关系句和解释段。关系句应能独立说明图表想表达什么，例如“定场景→采集→清洗→标注→评测，数据质量通过反馈循环持续提升”。同时明确哪一句是主判断，哪几句是证据，哪一句是注意事项。
5. 选择最贴合关系的图形。优先级依次为：定制场景示意 SVG、带测量/标注的示意图、真实数据图表、结构化卡片/矩阵、普通流程图。没有数量或比例时，不伪造柱高、百分比或精确坐标。
6. 图表负责结构，文字负责证据、边界和行动建议；强调块负责主结论和风险提醒。文字不要重复逐节点读图，应补充“为什么、何时适用、风险是什么、下一步怎么做”。
7. 交付前按信息单元逐项核对解释图：案例中的独立做法、每条判断条件、每个执行动作都能找到具体对象、变化或产物。编号卡、装饰图标、纯文字矩阵不能冒充解释覆盖。每个数字都有来源或明确标为示例；不确定内容标注为未知；图形不只依赖颜色，必要时同时使用标签、形状或线型。

## 图形选择规则

- 时间变化、阶段演进、版本记录：时间线。
- 先后依赖、落地步骤、数据管线：流程图。
- 反复迭代、模型与数据互相促进：闭环或飞轮。
- 采集层、治理层、服务层、团队层：架构分层图。
- 两种路径、技术路线、模型选择、优缺点：对照矩阵或双栏卡。
- 主体、系统、数据、价值出口之间的连接：关系图。
- 质量检查、交付条件、合规材料：检查清单。
- 多行业、多案例、多场景：案例卡组或场景分布图。
- 数量、比例、长尾、版本指标：条形图、折线图或排名图；只有在数据真实存在时使用数值图。
- 输入如何变成输出、抽取、匹配、分类：机制示意图或交互演示。
- 复杂行为可被拆成目标检测、规则或可观测事件：场景示意图，明确“简化后的判定规则”而不是声称模型理解了全部行为。
- 现实对象有明确外观或位置：依据参考用内联 SVG 画合理的对象轮廓、目标框和标注，核对前后朝向、开合结构与连接点，不要只写“设备”“现场”。
- 曲线与等级：先区分读曲线事实和运用专家规则。已给定映射时，将类别直接标到对应可见曲线或区域，明确轴、单位和比较尺度；未给定时用“读曲线事实 → 独立专家规则（待补）→ 等级输出”表达流程，不自造阈值、时长或三色波形映射。
- 两个目标是否接触、包含或相交：画原文定义的对象及空间关系；检测框相交只作定位候选，业务判定箭头必须注明规则来源及其证据边界。

## 长文本总结模式

对于会议录音、访谈、研究报告或多篇材料：

- 先给一条主线，再给按主题分组的视觉卡片。
- 按原段落顺序建立视觉库存表。每个卡片保存 `title`、`type`、`relation`、`must_show`、`evidence`、`boundary`、`implication`、`open_questions`。
- 对案例保留“场景→原始问题→简化/改造→数据动作→验证方式→结果或限制”。
- 对方法论保留“输入→处理→输出→反馈→版本记录”，让读者可以直接复用。
- 对含有口语、转写错误或观点冲突的材料，保留原意但不要把不确定说法改写成事实。
- 对缺少数值的比例关系，使用“相对示意”图并明确标注；不要用看起来精确的柱高或百分比冒充事实。
- 对课程、访谈或口述案例，保留“课程口径 / 未独立核验”等证据边界。

## 大模型微调与数据建设的默认方法论

将微调视为“任务定义、数据、评估、迭代”的工程闭环，而不是一次训练动作：

1. 先定义真实场景和可测输出，再决定是否需要微调。先用提示词、检索或工具调用建立基线；只有当问题具有稳定任务边界、可积累示例、且基线不足时才进入微调。
2. 拆任务而不是笼统地说“训练一个智能体”。把输入类型、输出格式、错误类型、允许的人工介入和验收指标写清楚。复杂业务优先拆成多个可观测子任务。
3. 建训练集、验证集、测试集并锁定划分规则。测试集应代表真实输入，避免同源样本、增强副本、同一事件或同一用户同时进入训练和测试。
4. 训练样本遵循“输入足够多样、输出足够一致、格式贴近生产”。混合正常、边界、困难、拒答和异常样本；用少量高质量样本校正方向，持续补充模型失败样本。
5. 评估不只看平均分。按场景、类别、长尾、严重错误和成本/延迟拆分指标；对关键错误建立人工复核。模型预测与既有标注差异大、loss 高的样本可作为标注反查入口，但必须人工确认。
6. 数据治理覆盖来源权限、隐私合规、清洗、标注、标准化、元数据、质量检查和可追溯版本。至少记录来源、用途、字段定义、标签规范、数据集版本、处理脚本、评估结果和责任人。
7. 对视觉或多模态数据，先检查清晰度、曝光、分辨率、坐标、码流、时间同步和标注对齐；用 embedding 相似度识别重复或增强注水；针对长尾补采真实困难样本，合成数据只作为有约束的补充。
8. 用“首版可用→模型反查→补失败样本→再训练”的数据飞轮推进。首批数据不必追求完美，但每轮都要记录变更、评估集版本和失败类型，否则无法解释模型是否真的变好。
9. 微调方式按目标选择：监督微调适合稳定的输入到输出映射、格式和行为；偏好优化适合风格、排序、摘要取舍；检索增强适合知识经常变化且需要引用来源；视觉微调适合图像输入理解问题。不能用微调替代实时知识库、权限控制或业务规则。

## 输出约定

默认输出顺序：

1. 一句主结论。
2. 一张真正的全景图，交代对象、输入、处理、输出与反馈。
3. 按信息块逐段给出视觉单元，每张图配一段解释；图数取决于独立关系的数量，判断表和执行清单逐项核对，不能只给一张总图。
4. 方法论、可复用模板和执行清单。
5. 已验证事实、基于证据的归纳、待验证问题。

如果用户明确只要文字，保持同样的结构化方法，但不生成可视化。若用户要求图片、网页或演示文件，先确认目标格式与尺寸，再调用相应工具或技能；不要把内联可视化误当成已交付的独立文件。

## 几何验收（硬门槛）

深色技术讲解页、独立 SVG 图解和任何使用 `data-layout-contract="v1"` 的页面，交付前运行：

```powershell
python scripts/audit_svg_layout.py output.html --channel msedge --strict `
  --json layout-report.json --screenshot layout-check.png

python scripts/audit_svg_layout.py output.html --channel msedge --strict `
  --viewport 390x844 --json mobile-layout-report.json --screenshot mobile-layout-check.png
```

必须满足：

- 每个契约图返回 `PASS`；旧图必须返回基础扫描 `PASS`，不能只返回 `SKIP`。
- 无节点重叠、文字溢出、文字重叠、连线穿框、连线穿字、连线交叉、标签压线和 viewBox 越界。
- 旧图至少不能出现 `TEXT_PATH_OVERLAP`、`TEXT_LINE_OVERLAP`、`TEXT_SHAPE_OVERLAP`、`TEXT_TOO_SMALL` 或 `TEXT_LABEL_TOUCHES_STROKE`。
- 浏览器控制台和页面脚本无错误。
- 声明 `data-required-visuals` 的分组内，每个应有条目都能找到唯一的 `figure.viz` 和实际 SVG；结构覆盖通过后另做逐项语义与可读性检查。
- 自动审计通过后仍需结合原文看截图，分别确认语义正确性、对象结构、曲线/区域标注、箭头方向和阅读顺序。

当前审计器会检查文字实际渲染字号，并把 `rect`、`circle`、`ellipse`、`polygon` 的边框纳入穿字扫描；契约图也执行这层扫描。带 `data-target-for` 的框会检查对象引用与几何覆盖。网格内的并排图不会被误判为上下相邻模块。`--viewport` 可切换桌面或移动端视口，移动端严格审计用于防止横向滚动图被缩放到 12px 以下。自动审计不能证明对象语义或物理结论正确，因此必须保留逐图语义复核；独立对象和物理装配按协议分别标记，不能通过合并节点规避描边检查。

若自动审计与截图结论冲突，先修图；不能以“看起来还行”覆盖机器报告。

## HTML 页面交付（两种锁定风格）

当用户要求生成网页、HTML 页面，或要求“图表 + 文字”的完整展示时，必须使用本 skill 的现成视觉系统，不要临时自创配色、字体、渐变或组件风格。

### 风格选择

- **深色技术讲解版（默认）**：深色卡片、蓝紫色线稿 SVG、场景标注、阈值图、长尾图。适合技术培训、方法论复盘、案例讲解、数据和 AI 主题。
- **QQ 浅色分享页版**：仅在用户明确要求浅色分享页风格、要求浅色底，或明确说保留上一版风格时使用。

### 深色技术讲解版（默认）

- `examples/demo-dark-body.html` 是完整深色示例（内容全部虚构）。后续整理新材料时复用其样式和组件，按新内容重建信息清单、图与覆盖声明，不把示例里的虚构对象、数字或记录 ID 带入新材料。
- 直接使用 `assets/dark-story.css`，不要改色板：页面 `#0f1218`、卡片 `#171c25`、面板 `#1d2432`、主蓝 `#7d97f5`、浅蓝 `#a3b5f8`、正文 `#e6eaf1`、次级 `#98a3b3`、绿色 `#51cf66`、橙色 `#f0955c`。
- 页面结构使用 `.wrap`、`.hero`、`.story-section`、`.section-head`、`.viz-card`、`.viz-scroll`、`.kv-grid`、`.logic-strip`、`.takeaway`、`.caution`、`.evidence`。
- 每张图放在 `figure.viz` 中，保留 `data-visual-id`、`data-visual-title`、`data-visual-type`、`data-visual-relation`、`data-visual-source` 五个属性，并写 `figcaption`。
- 每张复杂 SVG 的 `figure.viz` 同时声明 `data-layout-contract="v1"`，按 `references/svg-layout-protocol.md` 标记节点、连线和标签。
- 复杂视觉优先使用内联 SVG；每张 SVG 要有 `role="img"`、`aria-labelledby`、`title`、`desc`，所有坐标和文字必须在 `viewBox` 内。
- SVG 使用有重量层级的线稿、目标框、虚线、箭头和少量填色来标关系：关键框/路径加粗，辅助线变细，关键标签加粗；不要堆叠装饰性渐变、发光、玻璃拟态、远程图片或图标字体。
- 桌面保留完整的横向图解；移动端通过 `.viz-scroll` 横向滑动，页面本身不得出现横向溢出。
- 移动端横向滑动必须在图前提供可见提示，不能让右侧结论在无提示的情况下被裁掉。
- 若内容是纯流程，不要只画箭头方框；至少加入真实对象、状态、输入输出字段或一张判定表。流程顺序同时用独立 `.logic-strip` 或编号步骤表达。

### QQ 浅色分享页版（按需）

- 直接使用 `assets/qq-style.css`、`assets/qq-extra.css` 与 `assets/qq-responsive.css`，不要改写颜色、字体、圆角、阴影、间距或断点。
- 页面容器固定为 `.wrap`（最大宽度 880px），头部使用 `header.top` + `.kicker` + `h1` + `.lead`，章节使用 `.part`，内容模块使用 `.mod`。
- 每个视觉卡片使用 `figure.viz`，保留五项 `data-visual-*` 属性，并在卡片底部写 `figcaption`。
- 图标使用内联 SVG；不要使用 emoji、图标字体或远程图片。
- 页面必须自适应移动端；不要写死宽度，不要覆盖原 CSS 的媒体查询。

- `.scn` / `.scn-num` / `.scn-body` / `.scn-tag`：纵向编号场景列表，适合五项以内的场景说明；原分享页的“五大应用场景”即使用此组件。

### 生成与构建

1. 先按本 skill 的方法提炼内容，确定章节与视觉关系。
2. 深色技术讲解页以 `examples/demo-dark-body.html` 为结构参考；QQ 浅色页以 `examples/demo-light-body.html` 为结构参考。复制后替换内容，不改 CSS 语汇。
3. 用构建脚本组装完整页面。最后一个参数是主题：`dark` 或 `light`：

```bash
node scripts/assemble_story.js <shell.html> <run-dir> <body.html>
node scripts/build_recap.js <body.html> <output.html> "页面标题" dark
node scripts/build_recap.js <body.html> <output.html> "页面标题" light
```

4. 深色完整示例见 `examples/demo-dark.html`；QQ 浅色完整示例见 `examples/demo-light.html`，对应的正文片段见同目录的 `-body.html`。示例内容均为虚构。
5. 严格布局示例见 `assets/layout-contract-demo-body.html`；需要验证节点间距、连线通道和标签避让时先读该示例。
6. 运行 `scripts/audit_svg_layout.py`，保存 JSON 报告与截图；`--strict` 通过且语义、可读性审核通过后才交付。
7. 交付时给出生成的 HTML 绝对路径，并说明页面包含哪些章节、SVG 图、组件和审计结果。

### 内容与视觉的对应

- 主结论用 `.lead` 或 `.take`，不要做成大段摘要。
- 一个 `figure.viz` 只表达一个关系；关系句写在 `data-visual-relation` 和 `figcaption` 中。
- 文字解释放在 `figure` 前后，不重复逐节点读图，补“为什么、边界、风险、下一步”。
- 章节数量按材料决定，通常 4–6 个 PART；不要为了凑结构而拆空章节。
- 所有数字必须有来源或明确标为示例；无法验证的内容放进“证据边界”。
- 若一段原文同时包含“痛点、动作、结果”，优先使用三段式场景图或问题→动作→能力图，而不是三段纯文字。
- 若原文只给结论不给数据，使用结构关系图或相对示意，并在图注中明示“示意”；不得补造精确数值。
