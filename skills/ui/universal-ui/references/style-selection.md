# 风格选择

当用户没有锁定视觉方向，先给三个候选，不要直接实现。候选必须能被普通人一眼分辨，否则没有选择价值。

## 候选组合

1. **稳妥推荐**：最符合任务和信息密度的风格。
2. **偏好候选**：优先结合当前项目 `DESIGN.md`，再参考 `%USERPROFILE%/.codex/design-profiles/universal-ui.md` 的全局规则；Profile 不存在时使用 Neutral Core。
3. **个性候选**：可能更独特，但仍满足可读性、效率和产品气质。

如果三个候选中有两个来自同一风格家族，换掉一个。若用户明确要求某种成熟产品气质，允许其中一个候选做参考型转译。

## 输出格式

对每个候选给出：

```text
风格名：
一句话定位：
为什么适合：
首屏构图：
色彩逻辑：
字体与密度：
风险：
可从五个模板复用的组件：
```

同时给出推荐顺序和默认选择。用户未回复时，不得把“个性候选”直接当成已确认。

## 参考型项目

用户说“像 Codex / Notion / Magpie”时，先拆解参考对象：

1. 导航与工作区如何划分。
2. 主要对象的层级：项目、任务、会话、文档、运行。
3. 核心操作的位置。
4. 状态如何表达。
5. 哪些布局适合目标项目，哪些会破坏目标项目的功能。

参考结论写成文字或简版线框，再映射到三个风格候选。学习结构与交互逻辑，不做品牌像素复刻，不直接搬走商标、图标、文案和专有视觉资产。

## 原创型工具

用户只描述功能时：

1. 先从功能推导信息架构。
2. 按 [layout-patterns.md](layout-patterns.md) 选择布局。
3. 根据 `style-library.md` 匹配产品气质。
4. 若找不到完全匹配的风格，允许组合，但主导风格必须唯一。

不要因为功能独特就先堆装饰；先让任务路径成立，再用风格提升气质。

## 决策边界

- 任何候选都必须满足 12px 元数据下限、可见焦点、键盘主流程、浅色 / 深色等价和窄屏可用。
- 用户说“更漂亮”时，先问清是更柔和、更精致、更有个性还是更像某个产品；不要猜。
- 用户要求沉淀选择时，交给 `$ui-preference-ledger`；不要在 Universal UI 内直接写偏好。
