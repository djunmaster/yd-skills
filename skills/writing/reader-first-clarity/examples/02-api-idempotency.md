# 案例02｜软件/API：幂等性

**测试方向：** 技术概念解释、异常场景、准确性  
**场景说明：** 假设的支付接口场景。

## 原始表达

> 支付接口必须具备幂等性，避免网络超时或客户端重试造成重复扣款，确保交易处理的一致性。

## 通俗优化版

企业系统向银行发送一笔付款请求后，可能因为网络延迟，没有及时收到银行返回的结果。企业系统不知道这笔钱到底有没有付出去，于是可能再次发送同一笔请求。

系统需要识别这是不是已经处理过的同一笔付款。如果银行已经处理，就应返回原来的处理结果，而不是再执行一次付款。

因此，支付接口应提供一种识别重复请求的机制，并明确如何查询第一次请求的处理结果。

## 简单流程

1. 企业系统提交付款请求，并带上这笔请求的唯一编号。
2. 银行收到请求后，记录这个编号和处理结果。
3. 如果企业系统因超时再次提交同一编号，银行识别出这是重复请求。
4. 银行不重复执行付款，而是按约定返回原请求的结果。

## 新概念提示
- **API/接口：** 两个系统按照约定交换信息的连接方式。
- **幂等性：** 同一项业务请求重复发送时，不会重复产生实际业务结果。
- **超时：** 在规定时间内没有收到系统响应；超时不等于业务一定失败。
- **重试：** 没有及时收到结果时，再次发送请求。
- **唯一请求编号：** 用来识别某一笔请求的编号，帮助系统判断是否处理过。

## 准确性提醒
幂等机制的具体实现方式取决于接口设计。不能仅凭“支持重试”就认定不会重复付款；还要核实唯一编号的规则、保存时间、重复请求返回方式，以及不同请求是否可能误用同一编号。
